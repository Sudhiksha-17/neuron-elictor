1. WHAT THE DRY RUN SHOWED
   (results/grpo/20261116_175439_dry, 3 steps per phase, RTX 4090)

Pipeline
  - Ran end to end: setup check (9/9 pass), FineWeb max rescored on the 4090,
    Phase A, gate, Phase B, report, and a dry commit listing.
  - FineWeb maxes on the 4090 match the A100 values to within bf16 noise.

Phase A
  - Generation was 24-25 s per batch with merging on: the same as the 24 s
    measured with LoRA off and much faster than 41 s with LoRA. The merge does
    remove the LoRA slowdown.
  - A step takes about 33 s and peaks at 18.6 GB.

Phase B
  - Batch 256 ran out of GPU memory on every step and fell back to 128.
  - A step takes about 82 s and peaks at 24.5 GB.

New lead
  - 64 sequences took about as long as 128 (24 s vs 25 s), roughly 380 ms per
    generated token. Decoding seems limited by per-token latency, not batch
    size, so batch size may not be the main speed lever after all. The
    benchmark in section 4 should confirm this.

Scores
  - No signal after 3 steps, which is expected.
  - The gate failed (0.147 vs 3.047), and the trained score was below the
    untrained best-of-N for all 5 neurons.
  - Phase B ran anyway, apparently with the force flag.

Problems found
  - The out-of-memory fallback resets on every generation call, so it fails
    and retries each step.
  - The report's table header says "best of 64" when the dry run used 8.
  - The report says "Phase B was not run" when it was.
  - In dry mode the best-of-N baseline uses 64 samples instead of 192, so it
    isn't compute-matched.

Mismatch with CLAUDE.md
  - The code uses LoRA r=32/alpha=64 (CLAUDE.md says r=16/alpha=32), groups of
    16 (CLAUDE.md says 8), and prompts "Text:\n" and "<|nK|>\n" instead of the
    fixed template.
  - These may have been approved earlier, but CLAUDE.md doesn't record it.
    Either CLAUDE.md or the code should be updated.

2. hermes/grpo.py REVIEW

Done
  - merged() (hermes/grpo.py:90) keeps a pinned CPU copy of the base weights,
    merges the adapter, runs generation, unmerges, then copies the base weights
    back exactly.
  - It's used for training generation and the trained-sample eval when
    --merged_gen is set. The untrained evaluations never use it.

Missing
  - The bitwise-identity check every 50 steps.
  - The reference-text score at the start and end of each phase.
  - Any test of the merge path. scripts/test_grpo.py predates merged().
  - The Phase B neuron-token embedding rows aren't in the CPU copy; they rely
    on PEFT's own unmerge.
  - merge_adapter() sits outside the try, so a failure partway through would
    leave the weights partly merged with no restore.
  - The out-of-memory fallback should keep the smaller batch size across calls.
  - The CPU copy is about 7 GB of pinned memory and is copied back on every
    merged call; that cost hasn't been timed.
